# MongoDB and Redis credential-argv hardening: controlled rollout

This is an operator plan, not authorization to change production. Issue #242 removes passwords from MongoDB healthcheck and Redis startup/healthcheck process arguments; it does **not** rotate exposed credentials or prove a deployed system is safe. Deployment, MongoDB credential changes, container recreation, rollback, and backup/restore operations require the applicable owner approvals and a staffed window. No production operation was performed by this change.

The MongoDB healthchecks in both Compose files authenticate the configured root user against `admin` and then ping; authentication failure or an unreachable server is unhealthy. The API detailed health endpoint checks PostgreSQL and Redis, **not MongoDB**, so it is not a substitute for this check. Redis starts with a private generated `/tmp/redis-auth.conf` and authenticates its healthcheck using `REDISCLI_AUTH`. Its `appendonly yes` and `save 60 1000` settings and `/data` volume are unchanged. Redis config encoding preserves quotes, backslashes and other password bytes supported by environment variables.

This scope does **not** remove the separate upstream `mongo:7` first-initialization exposure: on an empty data directory, its entrypoint passes the root credential to `jq --arg` while creating the initial user. The existing-volume path skips that initialization. Do not claim all MongoDB process arguments are safe; track the upstream/bootstrap surface separately and do not initialize or recreate production storage to test it.

These changes remove plaintext from the affected process arguments, not from the container environment, Docker metadata or the private Redis config. Anyone with sufficient Docker/container or file access may still read secrets; restrict access and do not print rendered Compose, environment, config files, command histories, credentials, or auth URLs into logs, tickets or chat. The affected Mongo/Redis values may already have been exposed, so pursue the separate incident/rotation process even after rollout.

## Before the window

1. Obtain independent security/operations review of the exact candidate SHA and isolated-container evidence, including correct/wrong credentials, unreachable MongoDB, special characters, Redis startup failure and recovery, persistent configuration, and argv/log checks. If any check is missing or fails, stop.
2. Inventory the **actual** installed Compose/config revision, running image digests, container IDs, and MongoDB and Redis volume identities and mounts. Confirm that the staged file changes only the reviewed configuration, does not change images, volumes, dependency relationships, profiles or storage policy, and addresses the intended services. Account for existing drift before proceeding; never assume a project-prefixed volume name. Keep the scheduler and acquisition controls unchanged.
3. Record a tested rollback plan and preserve the previous Compose file and required configuration in restricted custody. Obtain a current verified backup, integrity evidence, and an appropriately isolated restore proof for each affected store before any change, in line with the applicable recovery runbooks. Preserve Redis AOF/RDB and MongoDB data; never remove or reinitialize volumes. Confirm backup owner, rollback authority and outage window.
4. Privately inventory the actual stored MongoDB user, all app/MCP/scheduler and backup consumers, encoded URLs, the Redis credential and every Redis consumer. Confirm the configured healthcheck credential authenticates the existing MongoDB user **before** recreation. `MONGO_INITDB_ROOT_*` initializes a user only for an empty data directory: editing these environment variables does not change an existing MongoDB account. Ensure backups are not running concurrently and establish who verifies the next scheduled backup.
5. Review rotation and rollback together. Password rotation is a separately authorized, coordinated change to the **stored MongoDB user**, the root-only environment/configuration and all consumers. Update URI-encoded connection strings as necessary and retain `authSource=admin` for the MongoDB root user. Redis uses the configured password when its server starts. Plan the exact order, outage, verification and recovery with the store owners; changing environment variables alone is not MongoDB rotation. Never restore an old env file as a substitute for reverting the stored MongoDB credential. A Compose rollback after rotation must continue to use credentials matching the actual stored account; restoring an exposed value requires an explicit incident decision.

## During an approved rollout

1. In the approved window, stage the reviewed Oracle Compose file at the reviewed SHA, compare it with the installed configuration, and validate it using `docker compose ... config --quiet` without printing the resolved environment. A `diff` exits 1 for expected changes; inspect and approve the actual diff rather than treating that status as a successful validation. Stop on unexpected drift.
2. Follow the approved credential and consumer sequence, if rotation is separately authorized. Do not place passwords on command lines. Do not rely on creating a new MongoDB volume, root-user initialization, or unauthenticated `ping` as proof of authentication.
3. Only after all prerequisites and authorization are met, the operator may recreate the intended MongoDB and Redis services without recreating unrelated services or removing volumes. Confirm the exact Compose project, files, environment and target services first; never use `down -v` or destructive cleanup. Expect a service interruption, reconnect/recovery time and potentially degraded Mongo-backed responses.
4. Verify both containers become healthy using the authenticated Compose checks; test the intended consumer connections and the API's Redis component separately. The MongoDB probe must report failure for incorrect credentials or an unavailable server; establish those negative cases in isolated disposable containers, not by disrupting production. Verify volume identities match the pre-change inventory and inspect process arguments and logs without displaying credentials. Verify persistence and the next backup using the authorized backup/restore process. Do not claim the detailed API health endpoint verifies MongoDB.

## Failure and rollback

Stop on failed authentication, unexpected volume identity, unavailable verified recovery, secret disclosure, unexpected dependency behavior, or failure to recover within the approved window. Preserve evidence without secrets and escalate to the owner. Prefer an approved forward fix; if rollback is necessary, restore the previously reviewed Compose/config with credentials matching the **current stored MongoDB user**, recreate only authorized services with the same volumes, and verify authenticated connections and backups again. The older configuration may reintroduce credential-in-argv exposure: record and contain that risk and rotate or revoke as directed by the incident owner.

This plan does not close the existing incident, verify current production state, authorize acquisition, or replace independent recovery/strict-watch acceptance. The previously accepted MongoDB backup script fix remains separate; its optional stdin/predictable-path and timestamp-collision follow-ups require their own disposition and are not included here.
