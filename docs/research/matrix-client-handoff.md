# Matrix client handoff: VniAgent and external MCP constraints

Research for [#37](https://github.com/Kohnnn/vnibb/issues/37), 2026-09-26. Repository observations are pinned to main [`20fa4c392e22a42b2d150de22989bb2331a98adb`](https://github.com/Kohnnn/vnibb/tree/20fa4c392e22a42b2d150de22989bb2331a98adb). Protocol citations distinguish the [2025-06-18 MCP revision](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization) from the [2026-07-28 revision](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization); the latter is documentation, not proof that VNIBB's installed SDK or a chosen client supports that revision. No service, provider, production database, or client was executed for this desk research.

## Answer in one paragraph

**Current:** VniAgent can accept a human-authored text question plus browser-supplied widget context/history and return an SSE answer with ephemeral source IDs and optional workflow outputs; its server prepares up to **three** symbol snapshots, optionally using the read-only MCP companion's two snapshot tools with direct-Postgres fallback. The browser also holds best-effort local notebook items and truncated run records. Separately, VNIBB's MCP exposes curated read-only market tools, policy/schema resources and prompts over stdio or Streamable HTTP, optionally protected by a *deployment-wide* bearer secret. Neither path currently takes a Matrix run ID or immutable reference and reopens an authorized saved result/evidence set. The shared bearer authenticates possession of a deployment secret, **not** the end user or their ownership of a Matrix run. **Required for release parity:** a stable scoped reference and separately authorized read resolution for both surfaces, a larger explicit selection policy, complete evidence/result retrieval, revocation/cache rules, and a tested named external client's exact supported transport/auth/tool/resource behavior. Both VniAgent and an external MCP-capable client are in release scope; neither automatic sending nor a particular external application has been selected. [Copilot API](https://github.com/Kohnnn/vnibb/blob/20fa4c392e22a42b2d150de22989bb2331a98adb/apps/api/vnibb/api/v1/copilot.py#L55-L85), [context builder](https://github.com/Kohnnn/vnibb/blob/20fa4c392e22a42b2d150de22989bb2331a98adb/apps/api/vnibb/services/ai_context_service.py#L584-L655), [MCP client](https://github.com/Kohnnn/vnibb/blob/20fa4c392e22a42b2d150de22989bb2331a98adb/apps/api/vnibb/services/vnibb_mcp_client_service.py#L16-L95), [MCP guard](https://github.com/Kohnnn/vnibb/blob/20fa4c392e22a42b2d150de22989bb2331a98adb/apps/api/vnibb/mcp/server.py#L1432-L1473).

## Protocol facts, not product commitments

- MCP resources are application-driven: a host may offer a picker, search or automatic context inclusion, but protocol **does not mandate** any one interaction. `resources/read` addresses a URI; templates allow parameters. Tools are model-controlled by design, with `tools/list` + `tools/call` and input/output schemas, but a host controls presentation/consent; the spec recommends user visibility/denial. Thus neither publishing a resource nor exposing a tool guarantees the external client will automatically attach a Matrix result. [Resources, 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/resources#user-interaction-model), [tools, 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#user-interaction-model).
- MCP HTTP authorization is optional at protocol level; **when adopting its OAuth profile**, protected-resource metadata, discovery, audience-bound tokens, per-request `Authorization` headers and validation apply. The [2026-07-28 authorization profile](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization#access-token-usage) and [2025-06-18 profile](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization#access-token-usage) differ in registration/discovery details. VNIBB's exact-match shared bearer and bare 401 JSON do **not** implement that user-delegation/discovery contract; it must not be described as OAuth end-user access. [VNIBB HTTP guard](https://github.com/Kohnnn/vnibb/blob/20fa4c392e22a42b2d150de22989bb2331a98adb/apps/api/vnibb/mcp/server.py#L1432-L1473). STDIO is instead expected to obtain local credentials from its environment ([authorization scope](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization#protocol-requirements)); local process authority is also not portable end-user ownership.
- The newer [2026-07-28 caching model](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/caching) distinguishes `ttlMs` freshness hints from guarantees, and `cacheScope: private` must not be shared across authorization contexts; changing underlying data and revocation require their own policies. The currently implemented server has no Matrix read/cached reference to revoke. Version negotiation matters: do **not** assume these 2026 fields or notifications are available in current Python SDK/external clients; a conservative server-side permission check on each Matrix resolution remains necessary even with client caching.
- The [MCP security guidance on token passthrough](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices#token-passthrough) explains why accepting a token issued for one resource and forwarding it to another is unsafe. A Matrix API credential, MCP audience credential and deployment secret have different issuers/subjects/scopes; specify each separately.

## Narrow interface candidates to evaluate (proposals, not chosen)

1. **VniAgent explicit selection:** A Matrix UI could present a user-reviewed selection, then send an opaque `matrix_run_ref` and optional *bounded* candidate IDs as distinct typed fields in the Copilot request, not pasted into `message` or inferred from capitalized text. The server resolves against the requesting user, an immutable run/version and declared candidate set; it produces a bounded context with structured observations and source/evidence references, refusing inaccessible/expired refs. Alternative: an explicit user-confirmed readable summary inserted as labeled low-trust context when durable resolution is not available; this does **not** establish parity with full evidence retrieval. No sending is implicit. [Existing Copilot request](https://github.com/Kohnnn/vnibb/blob/20fa4c392e22a42b2d150de22989bb2331a98adb/apps/api/vnibb/api/v1/copilot.py#L55-L85), [three-symbol builder](https://github.com/Kohnnn/vnibb/blob/20fa4c392e22a42b2d150de22989bb2331a98adb/apps/api/vnibb/services/ai_context_service.py#L584-L631).
2. **External read-only MCP:** Evaluate (a) a `vnibb://matrix/runs/{opaque_ref}` resource/template plus explicit result/evidence subresources, **if the named client supports discovery and user-selected URI reads**, or (b) a narrowly scoped `get_matrix_run` / `get_matrix_evidence` tool accepting opaque ref and bounded pagination **if the client reliably calls tools**. Both should resolve owner/consent/scope on every request, return immutable run version, candidate set, evidence identifiers, provenance/as-of and unavailable/stale status, enforce output size, and avoid secret-bearing URI parameters. A content-addressed public export could serve *only deliberately public* material and is not a substitute for protected user data. The existing snapshot tools/resources do not have this shape. [Server registrations](https://github.com/Kohnnn/vnibb/blob/20fa4c392e22a42b2d150de22989bb2331a98adb/apps/api/vnibb/mcp/server.py#L904-L1020), [resource read/template spec](https://modelcontextprotocol.io/specification/2026-07-28/server/resources#protocol-messages), [tool result types](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#data-types).
3. **Authorization/caching boundary:** Keep deployment bearer for trusted service-to-service access only if this remains private infrastructure; external per-user protected reads need a deliberate scheme compatible with the chosen client (e.g. proper MCP OAuth/resource-server integration), identity→Matrix ACL mapping, audience/scope checks, revocation behavior, TTL/no-store choice, and retained-export policy. Define whether revocation blocks future fetches only or also how already-fetched client copies and user exports are handled; deleting server permissions cannot retract data already in a host's model context or downloaded Markdown. Confirm lifecycle of immutable data versus live prices/news and exact evidence-not-found semantics. [MCP authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization), [caching](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/caching), [current browser-local export](https://github.com/Kohnnn/vnibb/blob/20fa4c392e22a42b2d150de22989bb2331a98adb/apps/web/src/lib/researchNotebook.ts#L147-L207).

**Minimum parity walkthrough (future acceptance, not executed):** one saved multi-candidate Matrix run with a stable reference; explicit human-initiated VniAgent send and an independently authorized *named* external client connection; both resolve the same frozen candidate IDs, result/version and evidence/observation set, report gaps rather than invent citations, reject unauthorized/expired refs, and recheck on revocation. Probe a selection >3 symbols, a deleted/rotated access grant, and a source containing instruction-like text. Capture client-visible UX and protocol traffic without real user data or provider calls. Tool-only client support does not prove resource picker support; a resource-capable Inspector test does not prove a chat host auto-includes resources. [Current limit](https://github.com/Kohnnn/vnibb/blob/20fa4c392e22a42b2d150de22989bb2331a98adb/apps/api/vnibb/services/ai_context_service.py#L584-L631), [protocol interaction models](https://modelcontextprotocol.io/specification/2026-07-28/server/resources#user-interaction-model).

**One named reference client, without choosing the user's app:** official [MCP Inspector](https://modelcontextprotocol.io/docs/2026-07-28/tools/inspector) is a *developer diagnostic candidate*. For a version-matched configured server, it can exercise transport connection, tool/resource listing and read/call responses and capture error paths; this would establish interoperability with **Inspector at its tested version**, not with all MCP clients, nor that a conversational client forwards a human-approved Matrix selection to an LLM. Separately choose/confirm the user's actual external MCP-capable client and test its transport, remote header/OAuth support, resource-template/read support, tool invocation approval, link opening, maximum output and cache/revocation behavior. No live client test was performed here.

## Decisions still open for product/implementation

- Which named external client and version, and does its real UX favor explicit resource selection, model-triggered tool calls, or a user-pasted summary/link? Both target clients remain required; automatic transfer requires separate consent/product design.
- What is the maximum selected candidate count/context byte budget and deterministic truncation/pagination rule beyond today's `[:3]`? Is a full result+evidence bundle or a user-selected subset required per send?
- Are Matrix results per-user private, shared with named collaborators, or intentionally public exports? Which identity provider/client registration/deployment model can enforce this without distributing the shared service bearer?
- What immutable snapshot identifier/version and evidence granularity (structured observations, source metadata, query timestamps, unavailable status) is owned by Matrix? How long is it retained; what happens after revocation, client caching and export?
- Which MCP protocol revision and SDK/runtime are targeted for the chosen client's parity test? Feature claims about 2026 authorization/caching must be checked against negotiated runtime rather than assumed from newest documentation.
