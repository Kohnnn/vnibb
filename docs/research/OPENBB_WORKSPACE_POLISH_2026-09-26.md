Neither documentation nor preview PNGs establish hosted Workspace's actual DOM, CSS, grid library, pixel row height, breakpoint schedule, clipping behavior or chart resize algorithm. The publicly inspected sources do not provide such an implementation; avoid saying it is definitively unavailable elsewhere. The docs also describe HTML, arbitrary SQL/Python and third-party iframe widgets, which are **outside VNIBB's requested safe/local scope**. No OpenBB Workspace service is required for the recommended local ideas.

A concept re-expressed locally is distinct from copying code/assets. Any actual copied MIT implementation/image requires preserving copyright/license notices; review the specific file and transitive dependency license before use. OpenBB's separate platform monorepo and published packages are **not** covered by these four MIT grants; the existing untracked `docs/openbb-assessment.md` in the shared checkout records AGPL-versus-Apache branch distinctions but is intentionally **not included or linked as a committed asset here**. Do not import OpenBB-platform AGPL code on the strength of an unrelated MIT repository or assume a future Apache branch changes published package terms.

The actual [`@openbb/ui` v0.14.0 package](https://github.com/OpenBB-finance/design-system/blob/8a35011409a58bc021660ead5fd36db9944e0d3a/packages/ui/package.json) declares `react`/`react-dom` peer range `^18.2.0`, Radix components, React Hook Form and Zod; its [root package](https://github.com/OpenBB-finance/design-system/blob/8a35011409a58bc021660ead5fd36db9944e0d3a/package.json) uses Yarn 4.3.1, and its [public exports](https://github.com/OpenBB-finance/design-system/blob/8a35011409a58bc021660ead5fd36db9944e0d3a/packages/ui/src/index.ts) are UI primitives, not a grid, widget shell, table or chart. VNIBB's [frontend manifest](https://github.com/Kohnnn/vnibb/blob/20fa4c392e22a42b2d150de22989bb2331a98adb/apps/web/package.json#L21-L50) is pnpm 9 / React 19 / Next 16 / Tailwind 4 and already depends on React Grid Layout, Recharts and Lightweight Charts. This is a **declared peer-range mismatch**, not a measured runtime incompatibility; installing a second UI stack for widget-fit work has no demonstrated payoff.

### Public implementation details versus hosted behavior

- OpenBB's [`Button.tsx`](https://github.com/OpenBB-finance/design-system/blob/8a35011409a58bc021660ead5fd36db9944e0d3a/packages/ui/src/atoms/Button.tsx) defines a size scale (xs 26px high, sm 32px, md 40px, lg 48px, xl 56px) and square icon buttons; [`GhostButton.tsx`](https://github.com/OpenBB-finance/design-system/blob/8a35011409a58bc021660ead5fd36db9944e0d3a/packages/ui/src/atoms/GhostButton.tsx) has a lighter icon-button focus treatment. Its [`screens.ts`](https://github.com/OpenBB-finance/design-system/blob/8a35011409a58bc021660ead5fd36db9944e0d3a/packages/ui/src/styles/screens.ts) breakpoints are 640/768/1024/1280px: **design-system tokens, not evidence of hosted Workspace grid breakpoints**. VNIBB already has a 32px toolbar and 640/768/1024px grid thresholds.
- OpenBB's [backend widget validator](https://github.com/OpenBB-finance/backends-for-openbb/blob/a6293707576e16edda8305adda95b07b6a4b968b/scripts/validate_widgets.py) emits a **warning** for widths outside 10–40 or heights outside 4–100, while invalid dimension **types** cause errors. Thus the documented 40-unit range is recommended, **not a proven hard runtime clamp**; neither samples nor metadata demonstrate that the hosted renderer enforces declared minima. Keep VNIBB constraints explicit in its own grid.
- The [parameter-positioning guide](https://github.com/OpenBB-finance/openbb-docs/blob/acd5b2bf2d8603f574bd6b2da2e15e1aae8b017d/content/workspace/developers/widget-parameters/parameter-positioning.md) describes a default top row and optional nested multi-row parameters with controlled visual order. This is **hosted UX documentation**, not reusable React header code; use it only to inform progressive disclosure of VNIBB's existing inline parameters in narrower measured cells.
- The [reference-backend Plotly configuration](https://github.com/OpenBB-finance/backends-for-openbb/blob/a6293707576e16edda8305adda95b07b6a4b968b/getting-started/reference-backend/plotly_config.py) sets `responsive: true` relative to its chart container and `doubleClick: reset+autosize`, with compact transparent layout margins. This is **Plotly-specific chart payload behavior**, not proof of hosted Workspace chart-shell resizing; VNIBB's existing Recharts/Lightweight Charts should be checked in their own explicit-height hosts instead of adding Plotly solely for a resize setting.

### Specific questions for a human fit/overflow decision

1. **Supported layout envelope:** agree on measured grid widths (e.g. narrow sidebar-constrained pane, mid-size and full-width), browser zoom (100%, 125%, 200%), standard and dense dashboard tabs, and which embed types are in scope. The numbers are *proposed test samples*, not observed OpenBB breakpoints.
2. **Resize invariant:** for each widget family (dense financial table, chart, compact KPI/strip, news/list, external embed), decide minimum usable *content* width/height versus grid `minW/minH`; if content needs wider than pane, horizontal scroll inside that widget (with keyboard access) or switch presentation, never silently lose essential columns/actions. Verify charts have a nonzero measured host after resize and maximize/restore; do not over-constrain manual resize.
3. **State invariant:** record `i,x,y,w,h`, tab, widget configuration, selected periods and visible table positions before toggling edit/view, opening sidebars, using browser zoom, refreshing/reloading, and cycling wide→narrow→wide. Assert only explicitly persisted states survive; narrow derived views must not overwrite the authored desktop layout. Check system-published dashboards separately: [`WIDGET_SYSTEM_REFERENCE.md` 253–282](https://github.com/Kohnnn/vnibb/blob/20fa4c392e22a42b2d150de22989bb2331a98adb/docs/WIDGET_SYSTEM_REFERENCE.md#L253-L282) says code fallback and database-published templates have separate update paths, with admin-specific settings/edit semantics.
4. **Header and overlay invariant:** long titles, linked-symbol picker, parameter controls, health badge, settings and overflow menu in narrow cells remain operable by pointer and keyboard; popover menus, error actions and focus affordances must not disappear under card clipping. Compare visual bounds by inspecting *actual browser geometry*, not source comments. Keep single header and appropriately scoped scroll areas; test sticky table headers and newest-column scrolling at zoom.
5. **Lifecycle invariant:** exercise initial skeleton/loading, no data, partial/stale, fetch error/retry, successful chart/table, collapsed and maximized states at each width. Verify useful error/empty information remains visible; changing content must not unexpectedly shrink a manually sized widget. Health/source correctness itself is governed by [data-trust map #24](https://github.com/Kohnnn/vnibb/issues/24), not this layout note.

## Recommendation order and exclusions

1. **Adopt (highest priority):** treat VNIBB's own widget size contracts and one persisted desktop layout as the authority; specify and browser-check fit/overflow/state invariants before changing code. OpenBB's explicit *widget-type dimensions plus saved layout state* demonstrate useful modeling, but VNIBB already implements most of it. Prototype narrow and wide headers plus one table/chart/strip first, with no new dependency.
2. **Adapt (only after observed fit gaps):** measured-container-driven compact chrome; per-widget scroll/column-width rules and explicit chart height; constrain *content* sizing without trapping manual resize; test persisted table/chart selection after restore. The OpenBB metadata and public examples inform contracts, not a drop-in implementation.
3. **Reject for this map:** wholesale 40-column migration, OpenBB grid/design-system replacement, importing the React 18-only UI package into VNIBB's React 19/Next 16/Tailwind 4/pnpm stack, external service or cloud-sync requirement, AG Grid Enterprise/Highcharts or new paid chart/grid license, copied preview screenshots/assets, arbitrary HTML/iframe/code execution and any claim that hosted Workspace is publicly source-available. OpenBB docs' optional technologies are not acceptance requirements for VNIBB.

**Handoff:** #44 is a fit-and-overflow research input, **not** the UI-runtime result or implementation approval. Prototype and human decision gates in [#43](https://github.com/Kohnnn/vnibb/issues/43) should settle the supported widths and interaction contract before any workspace change. [#35](https://github.com/Kohnnn/vnibb/issues/35) owns Matrix evidence playbooks/candidate analysis; [#24](https://github.com/Kohnnn/vnibb/issues/24) owns data trust and freshness semantics.
